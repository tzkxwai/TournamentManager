# Архитектура TournamentManager

## 1. О проекте

TournamentManager — приложение для проведения турниров и ведения рейтинга игроков.

Основные задачи проекта:
- создание и управление турнирами;
- добавление участников;
- автоматическое формирование турнирной сетки;
- проведение матчей;
- определение победителей;
- хранение результатов в базе данных.

## 2. Структура решения

Решение TournamentManager состоит из следующих проектов:

```text
TournamentManager
│
├── docs
│   ├── ARCHITECTURE.md
│   ├── DEVELOPMENT_LOG.md
│   └── PLAN.md
│
├── src
│   ├── PlayerService
│   └── TournamentService
│
└── tests
    ├── PlayerService.Tests
    └── TournamentService.Tests
```

### PlayerService

Отдельный сервис для работы с игроками.

Предполагаемые функции:
- управление игроками;
- хранение информации об игроках;
- управление рейтингом.

### TournamentService

Сервис для проведения турниров.

Реализованные функции:
- создание турниров;
- получение списка турниров;
- получение информации о турнире;
- формирование олимпийской турнирной сетки;
- сохранение матчей;
- запись победителей;
- создание следующих раундов;
- автоматическое завершение турнира.

Для генерации турнирной сетки используется отдельный класс `TournamentBracketService`.

### MatchService

Отдельный MatchService пока не реализован.

На текущем этапе работа с матчами находится внутри TournamentService.

В дальнейшем MatchService можно выделить в самостоятельный сервис.

## 4. Базы данных

Для хранения данных используется SQLite.

В TournamentService реализован контекст `TournamentDbContext`.

Основные таблицы:

### Tournaments

Хранит информацию о турнирах:
- Id — идентификатор;
- Name — название;
- CreatedAt — дата создания;
- IsFinished — статус завершения;
- PlayerIds — список участников.

### Matches

Хранит информацию о матчах:
- Id — идентификатор матча;
- TournamentId — идентификатор турнира;
- Round — номер раунда;
- Player1Id — первый участник;
- Player2Id — второй участник;
- WinnerId — победитель.

Для управления структурой базы данных используются миграции Entity Framework Core.

## 5. API TournamentService

Основные HTTP-маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | /api/tournaments | список турниров |
| GET | /api/tournaments/{id} | информация о турнире |
| POST | /api/tournaments | создание турнира |
| GET | /api/tournaments/{id}/bracket | получение или создание сетки |
| PUT | /api/tournaments/{id}/matches/{matchId}/winner | запись победителя |
| POST | /api/tournaments/{id}/next-round | создание следующего раунда |

## 6. Турнирная система

В первой версии используется олимпийская система соревнований.

Принцип работы:
1. Создаётся турнир.
2. Добавляются участники.
3. Генерируется первый раунд.
4. После завершения матчей записываются победители.
5. Из победителей формируется следующий раунд.
6. После определения победителя финала турнир автоматически завершается.

Результаты матчей сохраняются в SQLite.

Для завершённых турниров запрещено изменять результаты и создавать новые раунды.

## 8. Запуск программы

Для запуска TournamentService используется команда:

```powershell
dotnet run --project src/TournamentService
```

Для управления базой данных применяются команды Entity Framework Core:

```powershell
dotnet ef migrations add MigrationName --project src/TournamentService --startup-project src/TournamentService
```

```powershell
dotnet ef database update --project src/TournamentService --startup-project src/TournamentService
```

Для проверки API используется HTTP-запросы и OpenAPI в режиме разработки.

## 9. Безопасность

Авторизация с помощью JWT и разделение пользователей по ролям запланированы для следующих этапов разработки.

Предполагаемые роли:

- Admin — управление турнирами и результатами;
- User — просмотр турниров, матчей и рейтингов.

## 11. Принятые архитектурные решения

ASP.NET Core выбран для создания веб-сервисов на C#.

SQLite используется как простая и удобная база данных для учебного проекта.

Entity Framework Core применяется для работы с базой данных и управления миграциями.

xUnit используется для автоматического тестирования.

Архитектура предусматривает возможность дальнейшего разделения приложения на независимые сервисы.

## 12. Ограничения первой версии

На текущем этапе:
- поддерживается олимпийская система турниров;
- отдельный MatchService отсутствует;
- система рейтинга Эло не реализована;
- веб-интерфейс ещё не реализован;
- полноценная система авторизации находится в планах развития.

В дальнейшем архитектура будет расширяться по мере реализации новых возможностей.
